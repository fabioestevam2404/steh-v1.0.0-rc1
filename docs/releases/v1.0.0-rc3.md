# STEH MVP 1.0 Release Candidate 3

Release date: 2026-09-30

## Purpose

RC3 closes the gap between RC2 and the complete engineering workflow. It adds
the capabilities merged after RC2, moves agent execution out of the HTTP
request, and extends the acceptance contract to 25 criteria backed by 28
executable gates.

## Delivered

Workflow capabilities (ADR-009 to ADR-015):

- specification-driven development with `FR`/`NFR`/`AC` ids, Given/When/Then
  scenarios and a test plan before implementation;
- bounded rework connected to the graph, ending in `REWORK_EXHAUSTED`;
- durable Human-in-the-Loop decisions that resume the checkpoint once;
- auditable Context Engine with redaction, budgets, hashes and `UNTRUSTED`
  labels;
- read-only GitHub Issue Analysis and Pull Request Review behind a fail-closed
  repository allowlist;
- auxiliary, non-authoritative LLM-as-Judge evaluation.

Operational hardening:

- asynchronous execution through a PostgreSQL job queue and a worker process
  (ADR-016): `SKIP LOCKED` claims, renewable leases, `TASK_ABANDONED` on lease
  expiry, no automatic retries, and no raw content in job payloads;
- correlated structured logs (`task_id`, `trace_id`, `job_id`) across API,
  worker and agents;
- settings and database engine created on first use; injectable readiness
  that returns `503` when the database is unavailable;
- one-shot `migrate` service in Docker Compose;
- LF line endings enforced for shell scripts.

## Breaking changes

- `POST /api/v1/tasks`, `/from-github-issue`, `/from-github-pull-request` and
  `/{task_id}/human-review` return `202 Accepted` with `Location` and
  `Retry-After`. Clients poll `GET /api/v1/tasks/{task_id}` until `COMPLETED`,
  `BLOCKED`, `HUMAN_REVIEW`, `REWORK_EXHAUSTED` or `FAILED`.
- A worker must run for tasks to progress (`python -m app.worker`, or the
  `worker` Compose service).
- `GET /ready` returns `503` instead of `500` when the database is down.

## Upgrade

1. Apply migrations up to `0012_rc3_task_jobs` (the `migrate` Compose service
   does this).
2. Start at least one worker next to the API.
3. Update API clients to the `202` + polling contract.

## Verified baseline

The release candidate requires all criteria in
`docs/MVP-1.0-RC-ACCEPTANCE.md` (RC-01 to RC-25). The release workflow must
complete against the exact tag commit and retain its
`release-validation-evidence` artifact.

## Known limitations

- jobs are not retried and do not resume from the last checkpoint after a
  worker crash; the task fails closed with `TASK_ABANDONED`;
- queue depth and job latency are not exported as metrics;
- agent prompts live in code and are not versioned or hashed in the evidence;
- the acceptance suite does not yet cover: task blocking after an expired
  review, a negative judge verdict leaving the status unchanged, and task/job
  atomicity under database failure;
- RC3 is not a production security certification.

## Promotion

RC3 may be tagged only after its release PR is merged with green CI. Promotion
to `v1.0.0` requires a separate decision and evidence review.
