# STEH MVP 1.0 Release Candidate 4

Release date: 2026-10-01

## Purpose

RC4 hardens RC3 for trust and operation. It closes a validation gap that could
approve a task without validated code, lets the system survive worker restarts,
makes every agent prompt traceable in the evidence, and fills the acceptance
gaps RC3 had documented. It is the candidate for the `v1.0.0` promotion
decision.

## Delivered

Trust:

- **validation fails closed** when the workspace is empty or lacks a declared
  file; an empty workspace previously validated as PASS (PR #23);
- **versioned agent prompts** (ADR-018): the nine LLM agents load their
  instructions from `prompts/*.md` (moved verbatim, byte-identical), every agent
  run records the prompt id, version and SHA-256, and a lock file prevents
  unversioned prompt changes (PR #25).

Operation:

- **bounded job recovery** (ADR-017): an expired job is requeued up to
  `WORKER_MAX_ATTEMPTS` (default `2`) and resumes from the last LangGraph
  checkpoint, so only the interrupted node runs again; checkpoints are written
  synchronously; the implementation workspace is shared between `api` and
  `worker` (PR #24);
- **queue and task metrics** on `/metrics`, read from PostgreSQL so they are
  correct across replicas; the HTTP request counter, never incremented before,
  now counts every request by route template (PR #22).

Acceptance:

- new tests for expired-review blocking (RC-19), negative judge verdicts
  (RC-23) and task/job atomicity under database failure (RC-24);
- new criterion RC-26 for versioned prompts: 26 criteria, 30 executable gates.

## Breaking changes

- `steh_workflows_total` was removed from `/metrics` (it was never
  incremented); use `steh_tasks{status}`.

No API contract changes. Recovery is enabled by default; set
`WORKER_MAX_ATTEMPTS=1` to keep the RC3 fail-closed behavior.

## Upgrade

1. Rebuild the image (it now ships `prompts/`).
2. Recreate the Compose stack so `api` and `worker` mount the new
   `steh_workspaces` volume.
3. No new migration since RC3.

## Verified baseline

The release candidate requires all criteria in
`docs/MVP-1.0-RC-ACCEPTANCE.md` (RC-01 to RC-26). The release workflow must
complete against the exact tag commit and retain its
`release-validation-evidence` artifact.

## Known limitations

- if a worker dies while recording the post-workflow audit events, recovery can
  record some `POLICY_DECISION`/`REWORK_DECISION` events twice; task status and
  artifacts are unaffected (ADR-017);
- across hosts the workspace volume is not shared: a recovered job then fails
  `workspace_integrity` and regenerates the files through bounded rework;
- RC4 is not a production security certification.

## Promotion

RC4 may be tagged only after its release PR is merged with green CI. Promotion
to `v1.0.0` requires a separate decision and evidence review.
